# K3 — Cassa: route di lettura multi-sede + «Uscite del mese»

Stato: implementato il 2026-09-26 (ondata 1). Consumatore: **P4** (`CassaPanel` e finestre).

## Regola comune alle cinque GET

| query `scuola_id` | sedi lette |
|---|---|
| assente o vuota | **tutte le sedi attive** dell'utente (`resolveScuoleAttive`: SedeSelector ∩ accessibili) |
| uuid di una sede attiva | solo quella (`restringiSedi`) |
| uuid di una sede **non** attiva/accessibile | **403** `{ error, codice: 'SEDE_NON_ACCESSIBILE' }`: la cassa non viene letta, e resta un `warn` persistito `multi_sede` / `sede-filtro-fuori-scope` (`operazione`, `utente`, `ruolo`, `sede_id`, `sedi_attive`) |

- La lettura è **unita**; ogni sede resta però un cassetto a sé (fondo, saldo, svuotamento), quindi
  saldo e report restituiscono anche il dettaglio `per_sede`.
- Le **scritture** (POST movimenti, POST chiusura, POST/PATCH/DELETE categorie, storno) **non
  cambiano**: restano per sede con `resolveScuolaScrittura` (400 se ambigua, 403 se non propria).
  La UI deve mandare `scuola_id` nel body.
- `scuola_nome` viene da `schools.nome`. Se quella lettura fallisce vale `null` (con un `warn`
  `nomi-sedi-non-letti`), non si risponde mai 500 per un'etichetta. La UI ripiega sull'uuid, o
  sul nome che conosce dal SedeSelector.
- Utente senza sedi attive (e nessun `scuola_id`): elenchi vuoti, somme a 0, `per_sede: []`.
- L'ordine di `per_sede` è quello di `resolveScuoleAttive`: l'ordine del SedeSelector se c'è una
  selezione (il cookie), altrimenti sede primaria per prima, poi le altre.
- Helper condiviso: `src/lib/cassa/lettura-multisede.ts`, con `sediLetturaCassa`, `nomiSediCassa`
  e `meseCorrenteRoma`.

Tipi usati sotto: `RigaMovimentoCassa`, `SaldoCassa`, `CassaChiusura`, `CassaCategoria` e
`EntratoOggiVoce` in `src/lib/cassa/tipi.ts`, che non è stato modificato. I campi nuovi si
aggiungono con un'intersezione `& { scuola_nome: string | null }`.

## 1. `GET /api/pagamenti/cassa/movimenti`

Chi può chiamarla: tutto lo staff. Parametri query, tutti facoltativi: `scuola_id`, `da`, `a`,
`tipo` (`entrata|uscita|prelievo|rettifica`), `categoria_id`.

**Segreteria** (non Direzione): nessun KPI. Le chiavi `totali` e `uscite_mese` **non esistono**.
```ts
{ disponibile: true, movimenti: (RigaMovimentoCassa & { scuola_nome: string | null })[] }
```

**Direzione** (`admin`/`coordinator`, ruoli reali):
```ts
{
  disponibile: true,
  movimenti: (RigaMovimentoCassa & { scuola_nome: string | null })[],
  totali: {            // sul set FILTRATO (da/a/tipo/categoria), sommato su tutte le sedi lette
    entrate: number, uscite_contanti: number, uscite_altre: number, prelievi: number, rettifiche: number
  },
  uscite_mese: {       // MESE CORRENTE Europe/Rome, calcolato dal server, IGNORA i filtri
    da: 'YYYY-MM-01', a: 'YYYY-MM-<ultimo>',
    totale: number,
    per_sede: { scuola_id: string, scuola_nome: string | null, totale: number }[]  // una voce per sede letta, anche a 0
  } | null             // null solo se la lettura delle uscite del mese fallisce: mostrare «—».
                       // La risposta resta 200; il guasto va in un log `cassa`/`error`
                       // con esito `uscite-mese-non-lette` (niente `stato: 500`, che il client non riceve)
}
```
- Ogni riga porta `scuola_id` e `scuola_nome`. Per le entrate virtuali (`origine: 'incasso'`,
  `id: 'incasso:<uuid>'`) la sede è quella del **pagamento** dell'incasso. Un incasso il cui
  pagamento non ha sede (dato sporco) non si attribuisce a nessun cassetto: è escluso **sia dalla
  lista sia da `totali.entrate`**, contato in un `warn` `incassi-auto-senza-sede`.
- `uscite_mese.totale` comprende le righe `tipo='uscita'` con **qualunque metodo**: contanti,
  bonifico, carta e altro. Gli storni sono inclusi, e hanno importo negativo.
- Il riquadro «Uscite del mese» si alimenta con `uscite_mese.totale` e non più con
  `totali.uscite_contanti + totali.uscite_altre`. È il difetto corretto qui: quella somma dava le
  uscite di sempre.
- Schema cassa assente (DB CI): `{ disponibile: false, movimenti: [] }`.

## 2. `GET /api/pagamenti/cassa/saldo`

Chi può chiamarla: solo la Direzione. Parametro query: `scuola_id`, facoltativo.

```ts
type SaldoDiSede = { scuola_id: string, scuola_nome: string | null } & (SaldoCassa | { disponibile: false })

// tutte le sedi lette disponibili
{
  disponibile: true,
  fondo: number, saldo_atteso: number, entrate_contanti: number,
  uscite_contanti: number, prelievi: number, rettifiche: number,   // SOMME delle sedi
  entrato_oggi: EntratoOggiVoce[],                                  // fuso per metodo
  per_sede: SaldoDiSede[]                                          // ognuna col SUO fondo (cassa_config della sede)
}

// anche UNA sola sede non disponibile (schema assente o errore DB)
{ disponibile: false, per_sede: SaldoDiSede[] }                     // nessuna somma: sarebbe sbagliata
```
- Con `scuola_id`: la forma è quella di sempre, più `per_sede` di lunghezza 1.
- Ogni sede ha il suo `fondo`: il saldo di ciascuna si calcola a parte con `caricaSaldoCassa`, e le
  somme si fanno solo alla fine.
- `verificaSogliaCassa` si esegue per ogni sede letta, e mai su una sede che non è dell'utente.
- «Ultimo svuotamento per sede» non sta qui: si legge da `chiusura` GET, prendendo per ogni
  `scuola_id` la prima riga, perché l'ordine è `eseguita_il` decrescente.

## 3. `GET /api/pagamenti/cassa/chiusura`

Chi può chiamarla: solo la Direzione. Parametro query: `scuola_id`, facoltativo.

```ts
{ disponibile: true, chiusure: (CassaChiusura & { scuola_nome: string | null })[] }  // tutte le sedi lette, eseguita_il DESC
{ disponibile: false, chiusure: [] }                                                 // schema assente
```

## 4. `GET /api/pagamenti/cassa/report`

Chi può chiamarla: solo la Direzione. Parametri query: `scuola_id`, `da`, `a`,
`categoria_pagamento_id`, `format=csv`.

```ts
{
  disponibile: true,
  entrate_per_categoria: CategoriaEntrate[],   // SOMMATE su tutte le sedi lette
  uscite_per_categoria: CategoriaUscite[],
  mensile: ReportMensile[],
  per_sede: {
    scuola_id: string, scuola_nome: string | null,
    entrate_per_categoria: CategoriaEntrate[], uscite_per_categoria: CategoriaUscite[], mensile: ReportMensile[]
  }[]
}
{ disponibile: false, entrate_per_categoria: [], uscite_per_categoria: [], mensile: [], per_sede: [] }  // schema assente
```
- Con `scuola_id`: `per_sede` ha lunghezza 1.
- La sede di un'entrata è quella del **pagamento** (`pagamenti.scuola_id`); quella di un'uscita è
  `cassa_movimenti.scuola_id`.
- Un incasso il cui pagamento arriva **senza sede** (dato sporco) è scartato **prima** di calcolare
  gli aggregati: non entra né in cima né in `per_sede`, e si conta in un `warn`
  `cassa` · `incassi-senza-sede` · `quantita`. Stessa regola di movimenti. Così la somma di
  `per_sede[*].entrate_per_categoria` coincide sempre con `entrate_per_categoria` in cima.
- `format=csv`: il CSV contiene gli aggregati **in cima**, cioè quelli di tutte le sedi lette. Il
  formato del file non cambia.

## 5. `GET /api/pagamenti/cassa/categorie`

Chi può chiamarla: tutto lo staff, perché serve alla finestra dell'uscita. Parametro query:
`scuola_id`, facoltativo.

```ts
{ disponibile: true, categorie: (CassaCategoria & { scuola_nome: string | null })[] }  // ordine ASC
{ disponibile: false, categorie: [] }                                                   // schema assente
```
- Senza `scuola_id`: le categorie **globali** (`scuola_id: null`, `scuola_nome: null`) più quelle
  di **tutte** le sedi attive.
- Con `scuola_id`: le globali più quella sede.
- Senza sedi attive: solo le globali.
- Per la finestra di un'uscita su una sede S, la UI filtra
  `categorie.filter(c => c.scuola_id === null || c.scuola_id === S)`, oppure richiama la GET con
  `scuola_id=S`.

## Test

- `__tests__/cassa/lettura-multisede.test.ts`: **31 casi** (24 al primo giro, 6 aggiunti al
  secondo, 1 al terzo): 2 `meseCorrenteRoma`, 11 movimenti, 5 saldo, 4 chiusura, 5 report,
  4 categorie. Usano
  il client Supabase **finto che applica davvero i filtri** e tre sedi, di cui la C non appartiene
  all'utente. Per ogni route si prova una sede, più sedi e la sede non accessibile (con il `warn`
  `sede-filtro-fuori-scope`); per saldo, chiusura, movimenti, report e categorie anche l'utente
  senza sedi attive; per il saldo il caso misto (una sede disponibile, l'altra no). C'è anche
  `meseCorrenteRoma` al confine UTC/Roma.
- Prova di mutazione. Primo giro: **dieci** rotture del codice, dichiarate nel resoconto
  dell'esecutore di quel giro. Secondo giro: **nove** rotture, ciascuna ha fatto diventare rosso
  almeno un caso, poi il file è stato ripristinato:
  1. `uscite_mese` filtrata su `metodo='contanti'` → rosso «qualunque metodo e storni»;
  2. `uscite_mese` che salta gli importi negativi → rosso, stesso caso;
  3. `uscite_mese` a zero invece di `null` quando la lettura fallisce → rosso «uscite illeggibili»;
  4. log del guasto tornato a `logErrore({ stato: 500 })` → rosso, stesso caso;
  5. incasso senza sede scartato solo dalla lista → rosso «incasso senza sede» (`totali.entrate` 575 invece di 75);
  6. saldo che somma i soli cassetti disponibili → rosso «una NON disponibile»;
  7. saldo senza sedi risposto come non disponibile → rosso «senza sedi attive» del saldo;
  8. chiusura senza sedi che legge comunque `cassa_chiusure` → rosso «senza sedi attive» della chiusura;
  9. `sediLetturaCassa` senza il `warn` sul 403 → rossi i 5 casi «sede non propria».
- Terzo giro: un caso nuovo, «un incasso senza sede è scartato PRIMA degli aggregati» del report
  (orfano da 500 € fatto arrivare alla route col proxy `incassiSenzaFiltroSede`). Verifica che le
  entrate in cima siano 65 (l'orfano escluso), che siano uguali alla somma di `per_sede` e che ci
  sia il `warn` `incassi-senza-sede` con `quantita: 1`. Due rotture, ciascuna rossa, poi ripristino:
  1. il codice del giro 2 (orfano mappato con `scuola_id: null` e lasciato negli aggregati in cima)
     → rosso, «expected 565 to be 65»;
  2. `warn` non emesso → rosso sulla chiamata a `logEvento`.
- Quarto giro: nessun caso nuovo, ma due asserzioni sui log aggiunte a casi esistenti.
  - «un incasso senza sede non entra né nella lista né in totali.entrate» (movimenti) verifica
    anche il `warn` `incassi-auto-senza-sede` con `quantita: 1`.
  - «più sedi, una NON disponibile» (saldo) verifica anche l'`info` `saldo-non-disponibile` con
    `quantita: 1, sedi: 2`.

  Quattro rotture, applicate a coppie, poi il codice è stato ripristinato. Ogni coppia ha fatto
  diventare rossi esattamente quei due casi (2 falliti, 29 passati):
  1. movimenti, soglia del `warn` alzata da `> 0` a `> 99`, così il log non parte;
  2. saldo, `quantita: nonDisponibili + 1`;
  3. movimenti, `quantita: incassiSenzaSede + 1`;
  4. saldo, `logEvento` tolto.
- Test esistenti adattati. In tutti e sei (`movimenti-route`, `saldo-route`, `chiusura-route`,
  `report-route`, `categorie-route`, `degradazione-ci`) è cambiato il mock di `@/lib/auth/scope`:
  ora è asincrono e usa la `restringiSedi` **vera**. `resolveScuoleAttive` è stata aggiunta in
  `saldo-route`, `chiusura-route` e `report-route`; negli altri tre c'era già. In `saldo-route` e
  `report-route` il valore finto della sede nel `beforeEach` passa da `{ scuolaId: SC }` a `[SC]`,
  cioè la forma di `resolveScuoleAttive`. Anche il finto client Supabase è cambiato in quattro file:
  - `saldo-route`: prima era `{}`, ora è un builder (`from`, `select`, `in`, `then`) che risponde
    con un elenco vuoto. Serve ai nomi delle sedi; il saldo resta finto su `caricaSaldoCassa`;
  - `chiusura-route`: aggiunto `.in`;
  - `report-route`: aggiunto `.in`, e la tabella `schools` risponde con un elenco vuoto;
  - `categorie-route`: `from(table)` riceve la tabella, aggiunto `.in`, e `schools` risponde con un
    elenco vuoto.

  Nessuna asserzione esistente è stata toccata: nei sei file il diff non ha righe `expect(` né
  aggiunte né tolte.
