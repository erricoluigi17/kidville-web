# Contratto K1 — `GET /api/pagamenti`: lettura a blocchi oltre `max_rows` + `section_id`

File: `src/app/api/pagamenti/route.ts` (solo GET; la POST non cambia comportamento, eredita solo la
colonna in più nel join). Test: `__tests__/api/pagamenti-paginazione.test.ts`.

## Il difetto corretto

PostgREST taglia ogni risposta a `max_rows` righe (1000 in `supabase/config.toml`, 1000 il default
del progetto ospitato) **senza dirlo**. La GET non aveva `range`: restituiva le prime 1000 righe per
scadenza. In produzione il 26/09 i pagamenti erano **1.236** in tutto (746 nella sede più grande):
con le sedi accorpate KPI e tabelle della segreteria erano **già** tagliati.

## Richiesta (invariata)

```
GET /api/pagamenti?[alunno_id][&stato][&categoria_id][&scuola_id][&gruppo][&periodo]
                   [&scadenza_da][&scadenza_a][&fattura_stato][&solo_aperti]
```

- Staff (admin/coordinator/segreteria): perimetro = `resolveScuoleAttive` (tutte le sedi attive
  dell'utente, ristrette dal cookie `sedi_attive`). `scuola_id` restringe **dentro** quel perimetro,
  mai lo allarga. **Senza `scuola_id` si leggono tutte le sedi attive** — invariato.
- Genitore: solo i propri figli, filtri ignorati — invariato.

## Risposta 200 (forma invariata, una colonna in più)

```ts
{
  success: true,
  sedi: { id: string; nome: string; iban: string | null; intestatario: string | null }[],
  data: Array<{
    id: string
    alunno_id: string
    scuola_id: string            // SEMPRE presente
    scuola_nome: string | null   // SEMPRE presente (null se la lettura di `scuole` fallisce)
    // … colonne di `pagamenti` come prima (sconto/sconto_motivo se il DB le ha) …
    payment_categories: { id; nome; slug; colore; icona } | null
    alunni: {
      id: string
      nome: string | null
      cognome: string | null
      codice_fiscale: string | null
      classe_sezione: string | null
      section_id: string | null  // NUOVO (K1): serve al filtro classe (P2a / FiltroClassiContabilita)
      sospeso: boolean | null
    } | null
    residuo: number
    stato_effettivo: string
    causale_suggerita: string
    coda_stato?: 'in_coda' | 'in_invio' | 'errore' | null   // solo staff
    quota_id?: string; importo_totale_famiglia?: number     // solo genitore, voci split
  }>
}
```

**Tutte** le righe del perimetro, anche oltre 1000. Ordine: `scadenza` decrescente, poi `id`
crescente (prima era solo `scadenza`: fra righe con la stessa scadenza l'ordine era arbitrario, ora
è deterministico).

## Come legge

- A blocchi di `BLOCCO = 1000` con `.range(da, da + 999)`, fino al primo blocco **corto**
  (`< 1000`). Con esattamente 1000 righe servono 2 richieste (la seconda vuota).
- ⚠️ `BLOCCO` **non può superare** `max_rows`: un blocco tagliato dal server sembrerebbe corto e la
  lettura si fermerebbe lì. Se `max_rows` scende, `BLOCCO` scende con lui.
- Ordinamento **stabile** `order('scadenza', desc).order('id', asc)`: senza il secondo criterio due
  blocchi consecutivi si sovrappongono e perdono righe (i pari di scadenza sono la regola).
- **Tutto-o-niente**: se un blocco qualsiasi fallisce → **500** `{ error: 'Errore nel recupero dei
  pagamenti', details }` e `logErrore(evento: 'db')`. Mai una risposta parziale presentata come
  completa.
- DB non migrato (`42703` su `sconto`): il ripiego sul SELECT base rilegge **da capo**, a blocchi
  anch'esso.
- Tetto di sicurezza `MAX_BLOCCHI = 50` (50.000 righe), **tutto-o-niente anch'esso**. Dopo il 50°
  blocco pieno si legge **una riga di prova** (`range(50000, 50000)`):
  - prova vuota → le righe erano esattamente 50.000: risposta **200 completa**, nessun allarme;
  - prova con una riga → il perimetro ha davvero più di 50.000 righe: **500**
    `{ error: 'Troppi pagamenti per una sola lettura: restringi i filtri', codice: 'LETTURA_FALLITA', details: 'oltre 50000 righe' }`
    e `logErrore({ operazione: 'pagamenti:GET', stato: 500, evento: 'lettura-troncata' },
    new Error('lettura-troncata: oltre 50000 righe, 51 blocchi'))` (livello `error`, persistito: è
    raro e va visto). `logErrore` e non `logEvento`: solo `logErrore` alza la marca anti-doppione,
    e senza di lei `withRoute` scriverebbe sul 500 una **seconda** riga `route/error` più povera.
    Il test lo verifica (nessuna chiamata `logEvento(…, 'error', …)`, nemmeno da `withRoute`).
    Mai 50.000 righe presentate come tutte. Il `codice` è una **dipendenza aperta**, vedi sotto;
  - prova fallita → come un blocco fallito: 500 `evento: 'db'`.
- Non è una lettura transazionale: un pagamento inserito/cancellato fra un blocco e l'altro può
  spostare il confine. Accettato (la pagina si ricarica; prima il taglio era certo e permanente).

## Arricchimenti a pezzi (lunghezza URL)

- `fatture_coda` (badge `coda_stato`, solo staff e non `solo_aperti`): **per sede e stato, come
  prima di K1** — `.in('scuola_id', sedi).in('stato', attivi)`, niente filtro per `pagamento_id`,
  quindi l'URL è corto qualunque sia il numero di righe in elenco. Contro `max_rows` si legge a
  blocchi di `BLOCCO_CODA = 500` con `.order('id').range(…)`, **in sequenza**: di norma è UNA
  richiesta (le voci attive sono poche). 500 e non 1000 perché `leggiCodaAttiva` avvisa
  «coda-badge-troncato» su una risposta di 1000 righe, e un blocco pieno lo farebbe scattare a
  vuoto. Il ciclo si ferma al primo blocco corto **o al primo guasto**: un guasto (o la coda assente
  sul DB E2E non migrato) produce **una** riga `coda-badge-non-letta`/`coda-assente` per richiesta.
  Tetto `ceil(50000/500) = 100` blocchi, irraggiungibile (una voce attiva per pagamento, indice
  `fatture_coda_una_attiva_uidx`): se scattasse, `warn coda-badge-troncato`.
- `pagamenti_quote` (ramo genitore): `.in('pagamento_id', …)` a pezzi di 150; ora l'errore
  PostgREST è **controllato** e registrato (`logErrore evento: 'quote'`), prima era ignorato.
  Comportamento invariato: senza quota la voce split resta nascosta.
- `scuole` (nomi sede): invariata, gli id sono le poche sedi distinte.

## ⏳ Dipendenza aperta: il codice del 500 «troppi pagamenti»

Oggi la risposta porta `codice: 'LETTURA_FALLITA'`, che il client traduce «Non siamo riusciti a
leggere i dati. Riprova fra poco.»: **il consiglio è sbagliato** — riprovare non serve, serve
restringere i filtri. L'utente vede il testo tradotto del codice, non il campo `error`.

Non è una scelta chiusa: il codice dedicato va dichiarato in `src/lib/ui/esito-fetch.ts`, che è
**fuori dal perimetro di K1** (un codice non dichiarato lì fa rosso il lock `errori-con-codice`).
Proposta per il proprietario di quel file / l'orchestratore:

- `TROPPI_PAGAMENTI: 'erroreTroppiPagamenti'` in `esito-fetch.ts`;
- `messages/it/shared.json` → «Troppi pagamenti da mostrare insieme: restringi i filtri (sede,
  periodo, stato).»; `messages/en/shared.json` → "Too many payments to show at once: narrow the
  filters (site, period, status).";
- poi in `route.ts` `codice: 'TROPPI_PAGAMENTI'` e, nel test da 50.001 righe,
  `expect(j.codice).toBe('TROPPI_PAGAMENTI')`.

Il caso oggi è lontano (1.236 pagamenti in tutto il 26/09, il tetto è 50.000), e il log `error`
dice comunque la causa vera; ma finché il codice non esiste la dipendenza resta **aperta**.

## Log

| quando | evento | livello | campi (solo conteggi) |
|---|---|---|---|
| richieste a `pagamenti` > 1 | `pagamento` | `info`, **`persisti: false`** | `{ operazione: 'pagamenti:GET', esito: 'lettura-a-blocchi', blocchi, righe, sedi }` |
| oltre `MAX_BLOCCHI` (prova non vuota) → 500 | `logErrore` | `error` (persistito, UNA riga: `withRoute` tace) | `{ operazione: 'pagamenti:GET', stato: 500, evento: 'lettura-troncata' }` + messaggio `lettura-troncata: oltre 50000 righe, 51 blocchi` |
| blocco (o prova) fallito | `logErrore` | — | `{ operazione: 'pagamenti:GET', stato: 500, evento: 'db' }` |
| quote non lette (per pezzo fallito) | `logErrore` | — | `{ operazione: 'pagamenti:GET', evento: 'quote' }` |
| coda non letta / assente | `fattura` (da `leggiCodaAttiva`) | `warn` / `info` | una riga per richiesta |

`righe` = righe lette dal DB; `sedi` = sedi distinte fra le righe; `blocchi` = richieste a
`pagamenti` (compresa l'eventuale riga di prova). Nessun uuid, nessun nome.

**Perché `lettura-a-blocchi` non va in `app_log`.** `pagamento` è in `EVENTI_PERSISTITI`, ma in
`app_log` l'`ON CONFLICT` deduplica per (impronta, giorno) e **non aggiorna il `contesto`**: i
conteggi in tabella resterebbero quelli della prima apertura del giorno di quell'utente, cioè non
direbbero quanto pesa la lettura. È il riassunto di una richiesta, come `coordinate-bonifico` sullo
stesso percorso: va sulla console (Vercel), dove ogni richiesta ha i suoi numeri veri. Il test lo
blocca sul quinto argomento di `logEvento` (`{ persisti: false }`).

## Test

`__tests__/api/pagamenti-paginazione.test.ts` (15 test). Il finto è avvolto da un involucro che
emula `max_rows` (taglio a 1000) e rimescola `pagamenti`/`fatture_coda` prima di ogni lettura (i
pari di ordinamento in ordine arbitrario) e registra ogni `order` con la sua **direzione**
(`scadenza desc`, `id asc`); per il tetto una tabella virtuale genera le righe dall'intervallo
`range` chiesto. Coprono: 2500 righe in 3 blocchi **nell'ordine del contratto** (confronto con una
copia ordinata dei dati del fixture: scadenza decrescente, poi id crescente), `section_id`, 1000 esatte,
filtro sede, blocco fallito → 500, ripiego 42703 paginato, tetto 50.001 → 500 + UNA riga `error`
(nessun doppione di `withRoute`: la spia di `logErrore` richiama il logger vero, che alza la
marca), 50.000
esatte → 200 senza allarme, coda per sede/stato in 1 richiesta, 1200 voci di coda in 3 blocchi
sequenziali, coda guasta → 1 lettura e 1 log, genitore con 1400 voci in 2 blocchi (visibilità
ritardata e figli rispettati), quote a pezzi ≤150, pezzo di quote fallito → `logErrore quote` e
solo quelle voci nascoste.

## Per chi consuma (P2 / P2a)

- Il filtro classe può filtrare lato client su `r.alunni?.section_id` (può essere `null`: alunno
  senza sezione assegnata o archiviato).
- Le classi omonime in sedi diverse hanno `section_id` diversi: la chiave è `section_id`, e
  `scuola_id`/`scuola_nome` della riga dicono la sede.
- I KPI calcolati sulla risposta ora sono **completi** anche con più sedi.
