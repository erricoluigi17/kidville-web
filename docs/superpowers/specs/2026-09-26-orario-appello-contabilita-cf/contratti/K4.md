# K4 — Transazioni: divisione automatica per sede

Route toccate: `src/app/api/pagamenti/transazioni/route.ts` (GET, POST) e
`src/app/api/pagamenti/famiglia/route.ts` (GET). Consumatore previsto: P3 (`TransazioniPanel`).

## POST `/api/pagamenti/transazioni`

### Corpo

| campo | tipo | note |
|---|---|---|
| `pagante_parent_id` | uuid | obbligatorio |
| `scuola_id` | uuid, **facoltativo** | non decide più niente. Se c'è, deve essere fra le sedi attive (403 `SEDE_NON_ACCESSIBILE`). Il client nuovo **non** lo manda. |
| `metodo`, `riferimento`, `data_valuta`, `note` | come prima | copiati su ogni transazione |
| `importo_totale` | numero > 0 | Σ parti + eccedenza |
| `voci` | `[{ pagamento_id, importo }]` | sede = `pagamenti.scuola_id` |
| `ricariche_mensa` | `[{ alunno_id, importo, ticket }]` | sede = `alunni.scuola_id` (**difetto corretto**: prima andava nella sede dichiarata) |
| `voci_nuove` | `[{ alunno_id, categoria_id, descrizione, importo, scadenza, gruppo? }]` | **nuovo**, stessa forma di `componi`; sede = `alunni.scuola_id` |
| `voci_ticket` | `[{ alunno_id, quantita, costo_unitario, categoria_id?, scadenza?, gruppo? }]` | **nuovo**, stessa forma di `componi`; importo = `round2(quantita × costo_unitario)`; sede = `alunni.scuola_id` |
| `eccedenza_a_credito` | numero ≥ 0 | come prima |
| `conferma_eccedenza` | `'credito_famiglia'` | come prima (409 senza) |
| `sede_eccedenza` | uuid, **nuovo** | obbligatorio se eccedenza > 0 **e** sedi > 1; deve essere una delle sedi dell'operazione |
| `movimento_id` | uuid, **nuovo** | letto solo per rifiutarlo con più sedi; con una sede si ignora come prima (vedi sotto) |

Tetti **solo sugli elenchi nuovi** `voci_nuove`/`voci_ticket` (stessa forma di `componi`): 50 righe
per elenco, 60 fra i due (`MAX_RIGHE_*` importati da `conciliazione-registra`) → **400**.
`voci` e `ricariche_mensa` restano **senza tetto**, come prima del 26/09.

### Ordine dei controlli e risposte d'errore

1. zod → **400** `{ error: 'Dati non validi', details }`
2. nessuna riga → **400**
3. quadratura globale (Σ voci + ricariche + voci nuove + ticket + eccedenza ≠ totale) → **400**
4. eccedenza > 0 senza `conferma_eccedenza` → **409** `{ eccedenza }`
5. `scuola_id` dichiarato fuori dalle sedi attive → **403** `{ codice: 'SEDE_NON_ACCESSIBILE' }`
6. voce inesistente o in una sede non attiva → **403** `{ error: 'Una o più voci appartengono a un altro plesso' }` (nessun id nel corpo)
7. alunno (ricarica / voce nuova / ticket) inesistente o in una sede non attiva → **403**
   `{ error, codice: 'SEDE_NON_ACCESSIBILE' }` tramite `rifiutoSede` (lo stesso rifiuto del punto 5,
   `error` dal catalogo IT), senza id nel corpo
8. `movimento_id` presente:
   - sedi > 1 → **422** `{ codice: 'MOVIMENTO_PIU_SEDI' }`
   - sede 1 → **comportamento storico**: il campo si **ignora**, il pagamento si registra (200) e
     `movimento_id` non entra nel payload; si logga `info` `movimento-ignorato`.

   In nessun caso `movimento_id` arriva alla RPC: il legame col movimento bancario passa da
   `riconciliazione/[id]/componi`, che ha i gate (`puoConfermare`, fatture vive, importo del
   bonifico) che questa rotta non ha. (Il giro 1 rispondeva 422 `MOVIMENTO_NON_GESTITO` anche con
   una sede: deroga non richiesta, tolta al giro 2 in attesa di un'eventuale ratifica.)
9. eccedenza > 0:
   - `sede_eccedenza` non fra le sedi dell'operazione → **422** `{ codice: 'SEDE_ECCEDENZA_ESTRANEA' }`
   - sedi > 1 e `sede_eccedenza` assente → **422** `{ codice: 'SEDE_ECCEDENZA_MANCANTE' }`
   - sede 1 e `sede_eccedenza` assente → l'eccedenza va su quella sede
10. quadratura rifatta dopo la divisione (Σ dei totali per sede ≠ totale, succede solo con importi
    oltre il centesimo) → **400**
11. RPC assente (`PGRST202` / `42883`) → **503**; altro errore della RPC → **500** (nessuna
    scrittura: la RPC è tutto-o-niente)

Gli uuid del client (`scuola_id`, `sede_eccedenza`) si confrontano con `formaConfronto`: il
maiuscolo è la stessa sede.

### Divisione

- Un gruppo per sede, nell'ordine in cui le sedi compaiono (voci → voci nuove → ticket → ricariche).
- Payload di ogni sede = payload di `registra_transazione_contabile`:
  `importo_totale = round2(Σ parti della sede + eccedenza se è la sede scelta)`,
  `eccedenza_a_credito` > 0 su **una** sola sede, `pagante_parent_id`, `metodo`, `riferimento`,
  `data_valuta`, `note`, `registrato_da` copiati. `voci_nuove`/`voci_ticket` compaiono solo se
  non vuote (con una sede e senza righe nuove il payload è quello storico, chiave per chiave).
- **1 sede** → `rpc('registra_transazione_contabile', { p })`.
- **N sedi** → `rpc('registra_transazioni_per_sede', { p: { transazioni: [p1, …, pN] } })`.

### Risposta 200

```jsonc
{
  "success": true,
  "data": {
    // campi di sempre, dell'esito della PRIMA transazione (compatibilità)
    "transazione_id": "…", "incassi": 1, "ricariche": 0, "eccedenza": 0, /* … */
    // SEMPRE presente, lunghezza ≥ 1, stesso ordine dei gruppi
    "transazioni": [
      { "transazione_id": "uuid", "scuola_id": "uuid", "scuola_nome": "Kidville …", "importo_totale": 100 }
    ]
  }
}
```

`scuola_nome` è `null` se la lettura di `scuole` fallisce (si logga `nomi-sede-non-letti`, il
pagamento non si blocca per un'etichetta).

### Effetti dopo la scrittura

- Audit `registro_modifiche`: **una riga per transazione** (`record_id` = sua transazione,
  `nuovo_valore.sedi_operazione` = N). Errore d'inserimento → `warn` `audit-non-scritto`
  **per ogni transazione**, col suo `transazione_id` e l'errore PostgREST; la risposta resta
  **200** (l'incasso è già scritto) e le notifiche partono comunque. Prima era
  `.then(() => {}, () => {})`, un catch muto. Fissato dal test «audit NON scritto» in
  `__tests__/pagamenti/transazioni-divise-per-sede.test.ts`.
- Notifica `pagamento_registrato`: **una per sede**, con `scuolaId` della sede, gli alunni di
  quella sede ed `entitaId` = la sua transazione.
- Revoca della sospensione: su tutti gli alunni dell'operazione.

### Log (niente PII: solo conteggi, uuid, esiti)

- `logEvento('pagamento','info', { esito: 'transazione_divisa', sedi: N, transazione_1: 'uuid1', transazione_2: 'uuid2', … })`
  quando N > 1. **Una chiave per transazione**, non una stringa unita da virgole: `redact()` lascia
  in chiaro solo stringhe che sono per intero un uuid, e `'uuid1,uuid2'` uscirebbe `[redatto:…]`.
  Non un array perché il tipo `Valore` del logger non lo ammette.
- `info` `movimento-ignorato` quando arriva `movimento_id` con una sede sola.
- `logEvento('pagamento','info', { esito: 'transazione_registrata', transazione_id, sede_id, voci, voci_nuove, voci_ticket, ricariche, eccedenza })`
  per **ogni** transazione (successo dell'evento critico, persistito).
- `warn` `voci-fuori-sede` / `alunni-fuori-sede` con `n`; `error` `esito-rpc-inatteso`
  (`sedi: N`, `n: esiti ricevuti`), **una volta**, se la RPC divisa torna un numero di esiti
  diverso dalle sedi. La RPC non ha dato errore, quindi la scrittura è avvenuta: si risponde
  **200**, `transazioni` ha comunque N elementi (uno per sede, con `scuola_id`, `scuola_nome`,
  `importo_totale` della sede) e `transazione_id: null` dove l'esito manca; audit e notifiche
  partono con `record_id` / `entitaId` null per quegli elementi. Fissato dal test «la RPC divisa
  restituisce MENO esiti delle sedi».
- Il `KV_OK` (`logOk`) della richiesta riuscita lo emette già `withRoute` su ogni 2xx: una seconda
  chiamata qui duplicherebbe la riga. Il successo **persistito** è `transazione_registrata`.

## GET `/api/pagamenti/transazioni`

Righe invariate + due campi:
- `scuola_nome: string | null` (da `scuole`);
- `pagante_nome: string | null` — «Nome Cognome» del genitore (`parents.first_name/last_name`).

Una lettura fallita di `scuole` o `parents` degrada a `null` con un `warn`
(`nomi-sede-non-letti` / `paganti-non-letti`): il registro resta leggibile. Entrambi i casi sono
fissati in `__tests__/pagamenti/transazioni-get.test.ts` (un guasto non spegne l'altro campo).

## GET `/api/pagamenti/famiglia`

- `figli[]`: + `scuola_id: string | null`, `scuola_nome: string | null`.
- `voci[]`: + `scuola_nome: string | null` (della **voce**, `pagamenti.scuola_id`: è la sede che
  decide in quale transazione finirà).
- Lettura di `student_parents` o `alunni` fallita → **500** (prima diventava «nessun figlio» in
  silenzio); lettura di `ticket_mensa` fallita → **500** (prima ogni figlio mostrava
  `saldo_ticket: 0`). Stesso corpo `{ error: 'Errore nel recupero delle voci' }`.
- Lettura di `scuole` fallita → nomi `null` + `warn` `nomi-sede-non-letti`.

## Per P3 (`TransazioniPanel`)

- Non mandare più `scuola_id` (se lo mandi, dev'essere una sede attiva).
- Se le sedi delle voci selezionate sono più di una e c'è eccedenza: menu **Sede del credito**
  con le sole sedi dell'operazione → `sede_eccedenza`. I 422 `SEDE_ECCEDENZA_*` si mostrano col
  loro `error`.
- Esito: una ricevuta per ogni elemento di `data.transazioni`.
- Registro: colonne **Sede** (`scuola_nome`) e **Pagante** (`pagante_nome`).

## ⚠️ Da fare per chi possiede `esito-fetch.ts` e i cataloghi `messages/*/shared.json`

Il codice **`MOVIMENTO_NON_GESTITO` è orfano dal giro 2** e va **rimosso**, non lasciato lì:

- `src/lib/ui/esito-fetch.ts` — la voce `MOVIMENTO_NON_GESTITO: 'erroreMovimentoNonGestito'`
  (riga 3012 al 26/09);
- `messages/it/shared.json` e `messages/en/shared.json` — la chiave `erroreMovimentoNonGestito`
  (riga 607 in entrambi al 26/09).

Nato al giro 1, quando questa rotta rispondeva 422 `MOVIMENTO_NON_GESTITO` anche con una sede sola
(vedi il punto 8). Dal giro 2 la rotta **non lo emette più**, e nessun file in `src/` o `__tests__/`
lo usa (verificato con `grep -rn` il 26/09). Quei file sono fuori dal perimetro di K4: questo
contratto li **segnala** e non li tocca. Restano invece vivi, e vanno tenuti, i codici che la rotta
emette davvero: `MOVIMENTO_PIU_SEDI`, `SEDE_ECCEDENZA_MANCANTE`, `SEDE_ECCEDENZA_ESTRANEA`.
