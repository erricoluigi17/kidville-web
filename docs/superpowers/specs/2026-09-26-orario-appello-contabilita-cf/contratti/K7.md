# K7 — Registro ricevute con sede

**Route**: `GET /api/pagamenti/ricevute?anno=&userId=` (`src/app/api/pagamenti/ricevute/route.ts`)
**Consumatore**: `src/components/features/admin/pagamenti/FiscalePanel.tsx` (colonna Sede: compito UI, non K7).

## Perché

La numerazione delle ricevute è `UNIQUE (scuola_id, anno, numero)`: con tre sedi «n. 7/2026»
esiste una volta **per sede**. Il registro è già letto su tutte le sedi attive
(`resolveScuoleAttive`), ma finora non diceva di quale sede fosse ciascuna riga: due ricevute con lo
stesso numero erano indistinguibili.

## 🔴 Stato reale in produzione prima di K7: il registro dava SEMPRE 500

Misurato il 2026-09-26 con due `SELECT` in sola lettura sul DB collegato:

- `pg_constraint` su `ricevute_emesse`: tre FK soltanto — `pagamento_id`, `scuola_id`
  (`ricevute_emesse_scuola_id_fkey` → `schools`, **presente**) e `transazione_id`. **Nessuna FK su
  `alunno_id`**, e nessuna migrazione del repo la crea (`20260710130000` dichiara `alunno_id uuid`
  senza `REFERENCES`).
- `app_log`, route `pagamenti/ricevute`: codice `PGRST200`, messaggio «Could not find a
  relationship between 'ricevute_emesse' and 'alunno_id' in the schema cache», **14 occorrenze a
  500**, l'ultima il 2026-09-23 (più le 14 righe gemelle a 400 della fetch strumentata).

La select di prima conteneva l'embed `alunni:alunno_id ( nome, cognome )`, che PostgREST non può
risolvere senza FK: **ogni apertura del registro rispondeva 500**. La colonna «alunno» del contratto
non ha mai funzionato in produzione.

Conteggi a supporto (nessun dato personale): 144 ricevute, 144 con `alunno_id`, **0 orfani**
(`alunno_id` senza riga in `alunni`).

## Strada scelta: seconda lettura di `alunni` nella route (nessuna migrazione)

Due strade possibili:

- (a) migrazione `ricevute_emesse_alunno_id_fkey` — fuori dal perimetro di K7 (le migrazioni del
  lavoro sono già scritte e applicate, e non se ne creano altre). Con 0 orfani sarebbe applicabile;
  resta una **proposta** per il titolare, non fatta qui.
- (b) **scelta**: la route legge `alunno_id` e risolve nome e cognome con
  `.from('alunni').select('id, nome, cognome').in('id', ids)`, **a blocchi di 100 id**
  (`aBlocchi`/`ID_PER_QUERY` di `@/lib/db/blocchi`: gli id vanno nell'URL, oltre si prende un 414).
  `{ error }` controllato: un errore → 500 con `logErrore` (stesso punto di uscita `erroreDb` del
  registro, quindi nessuna risposta d'errore senza codice in più per il lock `errori-con-codice`),
  mai un registro senza nomi spacciato per completo. Funziona con o senza FK, quindi anche se un
  giorno (a) venisse applicata.
- **Isolamento**: anche la lettura di `alunni` dichiara la sede, `.in('scuola_id', sediAttive)`
  (lo impone il lock `isolamento-sede-coverage`, `alunni` ha `scuola_id`). Conseguenza misurata il
  2026-09-26: **2 ricevute su 144** hanno l'alunno oggi iscritto in un'altra sede; se quella sede
  non è fra le attive dell'utente, la ricevuta esce comunque (numero, importo, sede) ma con
  `alunni: null` (a schermo «—»). Scelta conservativa: sono dati di minori. Se il titolare vuole
  il nome anche in quel caso, serve una voce in `AMMESSE` del lock (fuori dal perimetro di K7)
  con la ragione «il nome è quello della ricevuta, che è già nel perimetro».

## Contratto della risposta (200)

```ts
{
  success: true,
  data: Array<{
    id: string
    pagamento_id: string | null  // null se il pagamento è stato cancellato (FK ON DELETE SET NULL, registro WORM)
    scuola_id: string            // NUOVO — uuid della sede che ha numerato la ricevuta
    scuola_nome: string | null   // NUOVO — schools.nome; null se la sede non ha nome
    numero: number
    anno: number
    importo: number | string
    periodo_competenza: string | null
    metodi: string[]
    tracciabile: boolean
    bollo: boolean
    annullata_il: string | null
    annullo_motivo: string | null
    creato_il: string
    // stessa FORMA dichiarata prima di K7, ma ora popolata davvero (prima: 500 in produzione).
    // null se la ricevuta non ha alunno_id, l'alunno non esiste più, o è oggi iscritto
    // in una sede fuori dalle sedi attive dell'utente.
    alunni: { nome: string | null; cognome: string | null } | null
  }>
}
```

`alunno_id` è letto ma **non** esce nella risposta: la forma resta quella di prima.

- Il nome sede arriva dall'embed PostgREST `schools:scuola_id ( nome )` (FK
  `ricevute_emesse_scuola_id_fkey`, migrazione `20260731122800_fk_scuola_id.sql`, **presente in
  produzione**). L'embed grezzo `schools` **non** esce nella risposta: il campo di contratto è
  `scuola_nome`. Se PostgREST lo restituisce come array, si prende il primo elemento.
- Invariati: gate (`requireStaff`), query `anno` (zod), perimetro `.in('scuola_id', sediAttive)`,
  ordinamento (`anno` desc, `numero` desc), `limit(500)`, filtro `.eq('anno', …)` solo se `anno` è
  dato, degradazione `{ success: true, data: [], disponibile: false }` su schema mancante (`42P01`,
  `42703`, `PGRST204`, `PGRST205`), 500 loggato con `logErrore` sugli altri errori.
- **FK verso `schools` assente (`PGRST200` sulla sede)** — sul DB E2E della CI, non migrato, la
  tabella può esistere senza il vincolo («mancheranno solo i vincoli», migrazione `20260731122800`).
  `PGRST200` **non** è in `SCHEMA_MANCANTE` (svuoterebbe un registro che esiste). Il ripiego scatta
  **solo** se il `PGRST200` riguarda la sede: `error.message` o `error.details` devono nominare
  `'scuola_id'` o `'schools'`. PostgREST nomina la **colonna** dell'embed, non l'alias (il messaggio
  reale di produzione dice `'alunno_id'`, non `'alunni'`), quindi per la sede il messaggio atteso è
  «… between 'ricevute_emesse' and 'scuola_id' …». In quel caso la route rifà **la stessa query
  senza l'embed `schools`** (stessa `leggi`: stesso perimetro, filtro `anno`, ordinamento e limite) e
  risponde con `scuola_id` valorizzato e `scuola_nome: null`, loggando
  `logEvento('db', 'warn', { operazione: 'pagamenti/ricevute:GET', esito: 'sede-senza-nome-fk-assente' }, errore)`.
  Un errore sulla query di ripiego segue le regole di sempre (schema mancante → lista vuota; altro
  → 500).
- **`PGRST200` su qualunque altra relazione** → 500 con `logErrore`, **nessun** ripiego e **nessun**
  warn sulla sede (non si dà la colpa alla tabella sbagliata).
- Con lo schema completo: **una** query sul registro + **una** su `alunni` per ogni blocco di 100
  alunni distinti (nessuna se nessuna ricevuta ha `alunno_id`).
- L'ordinamento resta per numero: righe di sedi diverse con lo stesso numero sono adiacenti. Chi
  vuole raggrupparle per sede lo fa in UI con `scuola_id`/`scuola_nome`.

## Test

`__tests__/api/pagamenti-ricevute-registro.test.ts` — 18 casi. Il finto riproduce lo **schema di
produzione**: simula la proiezione di PostgREST, risolve un embed solo sulle FK che esistono davvero
(`scuola_id`, `pagamento_id`, `transazione_id`) e a ogni altro embed risponde `PGRST200` con il
messaggio reale (che nomina la colonna). Registra per ogni query tabella, `select`, `eq`, `in`,
`order` e `limit`.

Prove di rottura eseguite (rompi → rosso → ripristina):

| rottura della route | test che diventano rossi |
|---|---|
| ripiego su qualunque `PGRST200` (il codice del giro precedente) | «PGRST200 su una relazione che NON è la sede» |
| tolto `.eq('anno', …)` da `leggi` | «con anno: … IDENTICI su query principale e ripiego» |
| rimesso l'embed `alunni:alunno_id` | 13 test su 18, fra cui «PRODUZIONE: nessuna FK su alunno_id» |
| `.in('id', ids)` senza blocchi | «molti alunni → lettura a blocchi», «… nessuna lettura di alunni» |
| tolto l'ordinamento per `numero` | i due test su filtro/ordinamento/limite |
| ripiego solo se il messaggio nomina `'schools'` | i 4 test del ripiego sulla sede |
| tolto `.in('scuola_id', sediAttive)` dalla lettura di `alunni` | «PRODUZIONE…», «isolamento: … FUORI perimetro» |
